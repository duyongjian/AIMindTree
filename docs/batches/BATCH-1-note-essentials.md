## R-01 ｜ 笔记自动保存

### 一句话

编辑笔记时不用手动点保存了，停手 2 秒自动存，切走/退出前强制存一次。

### 为什么要做

现在保存**只有手动**（AppBar 保存按钮），忘点就丢内容。这是编辑器最基础的体验底线——用户不会接受"记了半天笔记，关掉就没了"。

### 现状证据（代码实地）

| 事实 | 位置 |
|---|---|
| 保存仅手动（AppBar 保存） | `lib/features/notes/note_editor_page.dart:419` |
| 脏标记：只比较序列化缓存，移动光标不置脏 | `note_editor_page.dart:117-123` |
| 打开顺序：先写 `_lastBody` 再 `setMarkdown`（顺序反了会误标脏） | `note_editor_page.dart:125-135` |
| 保存即入同步 outbox | `APP_CURRENT_STATE.md` §4.5 第 5 条 |
| 每次变更全篇重算序列化 + 整列重建，长文（≥3000 行）性能未优化 | §4.5 第 2 条 |

### 怎么做

1. 在 `note_editor_page.dart` 加 **debounce 定时器**：停止输入 **2s** 触发保存；长文（>3000 行）放宽到 **5s**（该阈值为估算值，需实测后回填）。
2. **复用现有保存函数**，禁止另写一条序列化/写库路径——保证与手动保存同一出口、同样入 outbox。
3. 触发条件用**现有脏标记**判定（不新增判据），没脏就不写库、不入 outbox。
4. 补充触发时机：编辑器失焦、切 Tab、退出编辑器、应用退到后台 → **立即 flush 一次**（防丢最后一句）。
5. 状态反馈：顶部或编辑器角落显示轻量文案「保存中…」→「已保存」+ 时间戳。**禁止弹窗/打断输入**。
6. 手动保存按钮**保留**，与自动保存走同一函数，不产生重复 outbox 记录。

### 验收标准（GWT）

| # | Given | When | Then |
|---|---|---|---|
| 1 | 用户编辑笔记 | 停止输入 2s | 内容落库、`updatedAt` 更新、入 outbox；界面显示「已保存」 |
| 2 | 打开笔记**不做任何编辑** | 停留 10s（自动保存触发多次） | `content_md` 的 sha1 与打开前**完全一致**；outbox **无新增记录** |
| 3 | 点手动保存 | 与自动保存同时发生 | 二者不冲突，outbox 不出现重复记录 |
| 4 | 编辑中切 Tab / 退出编辑器 | 离开 | 立即 flush，无内容丢失 |
| 5 | 长文（≥3000 行） | 连续输入 | 不出现输入卡顿（自动保存不得阻塞输入线程） |

### 风险与红线

- **RK-01（高）**：自动保存与 **L1 字节直通**冲突。风险在于自动保存若改写了未编辑块的 `source`，会把"打开就变脏""同步假冲突"这两个刚治好的老毛病带回来。
  - 约束：自动保存**只写用户已编辑的块**；未编辑块 `source` 保持直通。
  - 强制回归断言：打开笔记不编辑 → 触发保存 N 次 → `serialize(parse(md)) == md` 成立、sha1 不变。
- 红线 #1（L1 字节直通）、#6（新增写库点必须触发刷新）、#8（禁裸 catch）。

### 估算

**0.5–1 人天（估算）**

## R-02 ｜ 笔记回收站 + 恢复

### 一句话

删掉的笔记进回收站，能看、能恢复、能彻底删除——和知识点回收站一模一样。

### 为什么要做

现在**知识点有回收站，笔记没有**（§13-B 明确列为"功能割裂"）。误删一篇笔记 = 永久丢失，且用户会困惑："为什么知识点能恢复，笔记不能？" 本版主题就是消除割裂，这条自相矛盾没有道理。

### 现状证据

| 事实 | 位置 |
|---|---|
| 笔记删除是**软删**（写 `deletedAt`），列表过滤掉已删 | `lib/main.dart:298-312` |
| 删除入口 | `lib/main.dart:391` `_deleteNote` |
| 知识点有回收站（可恢复 / 彻底删除） | `knowledge_recycle_bin_page.dart`；`knowledge_repository.dart:527-584` |
| 知识点软删支持三选：留树 / 从勾选树摘除 / 彻底删除 | `knowledge_repository.dart:411-525` |
| **笔记恢复：未实现** | §4.1 表格最后一行 |

### 怎么做

1. **先做一步核查（必做前置）**：确认"删除笔记"当前的级联范围——笔记软删时，其知识点 / 画布节点 / 附件（note_assets）分别怎么处理？**把结论写回本文档再动手**，因为它直接决定"恢复"能恢复到什么程度。
2. 新建 `lib/features/notes/note_recycle_bin_page.dart`，**复用 `knowledge_recycle_bin_page.dart` 的交互骨架**（列表 + 恢复 + 彻底删除 + 清空回收站）。交互一致性是这条需求的核心价值，不要另起一套。
3. 数据层新增（放 `notes_repository` 或对应 repo）：
   - `listDeletedNotes()`：查 `deletedAt` 非空，按删除时间倒序
   - `restoreNote(id)`：清 `deletedAt` + `version + 1` + **入 outbox**（作为正常 upsert，不是墓碑）
   - `purgeNote(id)` / `purgeAll()`：真删行 + 清理该笔记的孤儿 `note_assets`
4. 入口：笔记列表页（`main.dart` 笔记 Tab）AppBar 或抽屉加「回收站」，显示待清理数量（可选）。
5. 同步语义：恢复 / 彻底删除都必须入 outbox，保证跨设备一致。
6. 彻底删除要有**二次确认**，文案明示"不可恢复"。

### 验收标准（GWT）

| # | Given | When | Then |
|---|---|---|---|
| 1 | 删除一篇笔记 | 打开回收站 | 可见该笔记，显示删除时间 |
| 2 | 回收站中点「恢复」 | 确认 | 笔记回到列表；标题/正文/附件完整；`updatedAt` 更新；入 outbox |
| 3 | 恢复后 | 在另一设备拉取 | 该笔记可见（同步一致） |
| 4 | 点「彻底删除」 | 二次确认 | 从回收站消失、不可恢复、孤儿附件被清理 |
| 5 | 删除笔记时选择了级联处置 | 恢复 | 恢复结果与第 1 步核查结论一致（并在 UI 上明示哪些东西不会自动回来） |

### 风险与红线

- **新增风险 RK-09（中）**：笔记删除的级联范围未确认，恢复语义可能与用户预期不符。应对：第 1 步核查先行；恢复时若知识点/树成员不自动恢复，必须在 UI 明确提示，不能静默。
- 红线 #7（不改 `canvas_nodes` 行语义）、#5（同步契约：新增字段/列需上行）、#6（触发刷新）。

### 估算

**1–2 人天（估算）**，含第 1 步核查 0.5 天。

## R-03 ｜ 笔记搜索

### 一句话

笔记列表顶上加个搜索框，输关键词能搜标题和正文。

### 为什么要做

现在列表页**没有搜索框**（§4.1），笔记一多就找不到。这是笔记类产品的检索底线能力。

### 现状证据

| 事实 | 位置 |
|---|---|
| 列表按 `updatedAt` 倒序，过滤 `deletedAt.isNull()`；**无搜索框** | `lib/main.dart:299-312` |
| 全仓无笔记搜索实现 | §4.4「笔记搜索 ❌ 未实现」 |

### 怎么做

1. 笔记列表页顶部加搜索框（与知识点管理页的搜索框风格保持一致）。
2. 匹配范围：**标题 + 正文（`content_md`）**。
3. 防抖 **300ms**。
4. 实现方式：数据量小（自用阶段几十到几百篇），**直接内存过滤或 SQL `LIKE` 即可，明确不做 FTS 全文索引**（避免过度设计）。
5. 空态：无结果要有引导文案（例："没有匹配的笔记，换个关键词试试"）。
6. 命中高亮：**本期不做**（记入后续），先保证搜得到。
7. **需拍板**：搜索范围是「当前笔记本」还是「全局所有笔记」？建议默认当前笔记本 + 提供"全部"切换。

### 验收标准（GWT）

| # | Given | When | Then |
|---|---|---|---|
| 1 | 笔记 ≥50 篇 | 输入关键词并停止 300ms | **≤300ms** 返回结果；标题命中与正文命中都能检出 |
| 2 | 关键词无匹配 | 搜索 | 展示空态引导文案 |
| 3 | 清空搜索框 | 输入为空 | 恢复全量列表 |
| 4 | 已删除（回收站中）的笔记 | 搜索 | **不出现**在结果里 |

### 风险与红线

- 低风险。唯一注意：搜索必须沿用列表的 `deletedAt.isNull()` 过滤，别把回收站里的笔记搜出来（验收 #4 已覆盖）。
- 若数据量将来上千篇，`LIKE` 会慢——届时再评估 FTS（记后续版本池）。

### 估算

**0.5 人天（估算）**
