## 1. 问题陈述

用户原话：

> 「知识点点进去的老师模式讲解功能退出后再进会把原来讲解丢失，而且老师模式的讲解和追问功能是否冗余呢，两个是否是一回事，我希望老师的讲解功能和追问功能合并，并且加入会话管理上下文和增删改查会话，一点进知识点可以进入主会话就是自动讲解一下，后面可以继续用这个会话也可以新建会话继续问问题。」

拆成四个**互相独立**的问题（第 4 条为技术预研阶段新发现的缺陷，见 §1.4）：

### 1.1 问题 A：讲解「丢失」——缺陷修复（数据没丢，是 UI 没回填）

| 项 | 内容 |
| --- | --- |
| 用户可感知现象 | 第一次点进知识点的老师模式，讲解正常显示；**退出页面再进入**，「讲解」区域变成「暂无讲解，点『重新生成』」，需要重新生成一次才能看到。而用户清楚自己刚看过。 |
| 期望行为 | 进入老师模式即可看到该知识点此前生成过的讲解，历史讲解**永久可见、可回溯**。 |
| 根因（已核实） | `teacher_page.dart` 的 `_bootstrap()`（78–97 行）确实从库里读出了历史讲解消息 `explainMsgs`，但 94–96 行**只把它用作「是否生成过讲解」的判断**：`if (explainMsgs.where((x) => x.role == 'assistant').isEmpty) { _generateExplain(); }`——**从未把历史讲解回填进 `_explainText`**；而 UI 只渲染内存变量 `_explainText`（`_ExplainPane`）。**数据在 `ai_messages` 表里从未丢失，丢的是界面回填。** |
| 性质判定 | **缺陷修复**，不是数据迁移。修复方向：UI 改为以「会话消息流」为唯一数据源（读库渲染），不再依赖一次性内存变量。 |

### 1.1b 附带发现的同类缺陷（必修项，独立于问题 A）

| 项 | 内容 |
| --- | --- |
| 现象 | 老师模式的会话被删除后再次进入该知识点，**复用一个已软删的空壳会话**（其消息也已被软删）→ 永远显示空。 |
| 根因（已核实） | `ai_session_repository.dart:55-58` 的 `getOrCreateForKp` 查询**漏了 `deletedAt.isNull()` 过滤**；而同文件另三处同类查询（`listAgentSessions:177`、`listMessages:118`、`clearMessages:208`）**都过滤了** → 属明确遗漏，非设计。 |
| 影响 | ① 直接制造「进入老师模式一片空白」的假故障；② **破坏老数据合并的幂等性**——合并的幂等条件正是「存在未删的 explain 且存在未删的 chat」，若查询捞回墓碑行，重复进入会反复触发合并。 |
| 结论 | **必修**：所有会话查询一律带 `deletedAt.isNull()`；验收见 §9-A5 / §9-A7。 |

### 1.2 问题 B：讲解与追问冗余——产品形态调整

| 项 | 内容 |
| --- | --- |
| 用户可感知现象 | 老师模式页有「讲解 (T6)」「追问 (T5)」两个 Tab。讲解 Tab 是一段**只读文本**（不记在消息流里），追问 Tab 是**聊天气泡**。两个 Tab 讲的是同一个知识点的同一件事，用户要在两者之间来回切，且「刚听过的讲解」在追问时不会作为上下文被继承。 |
| 期望行为 | 讲解与追问是**同一条消息流**：进入知识点先自动讲一次，之后在同一处继续问；AI 能看到自己刚才讲过的内容。 |
| 现状事实 | 两个 Tab **各持一个独立会话**（`getOrCreateForKp(kpId, task)`，`ai_session_repository.dart:253-260` 按任务码映射 type：T5→`chat`、T6→`explain`），因此 `ai_sessions` 里同一 KP 下躺着**两行**会话；`_ExplainPane` 的内容不进消息流。 |
| 性质判定 | **产品形态调整**（信息架构变更），非缺陷。 |

### 1.3 问题 C：缺会话管理——功能新增

| 项 | 内容 |
| --- | --- |
| 用户可感知现象 | 老师模式只能被动用「一条固定会话」：不能新建第二个会话、不能查看历史会话、不能重命名、不能清空、不能删除。用户想「换个话题另开一段问」只能退出重进，而重进又会命中问题 A。 |
| 期望行为 | 老师模式具备与 AI 助手 Tab 同等的会话管理能力：增（新建）、删（删除）、改（重命名 / 清空）、查（会话列表 / 切换）。 |
| 可复用先例 | `lib/features/agent/agent_page.dart:1520+` 的 `_SessionManagerSheet` 已是成熟实现（列表 / 新建 / 重命名 / 清空 / 删除），配套 `deriveSessionTitle`（:180-195）、`fmtSessionTime`（:198-205）、`askNameDialog`、`confirmDialog`；仓储层 `renameSession / clearMessages / deleteSession` 均已实现。**本次复用，不另起炉灶。** |
| 性质判定 | **功能新增**。 |

### 1.4 问题 D：多轮追问当前**无记忆**（技术预研新发现，必修）—— **本次改造的首要目标**

| 项 | 内容 |
| --- | --- |
| 用户可感知现象 | 在老师模式里连续追问：「什么是反向传播？」→「那它的梯度怎么回传？」——第二个问题的回答**与第一个问题无关**，AI 像是完全没听见上一句。 |
| 期望行为 | 同一会话内**后一轮能引用前一轮**的内容（用户说的、刚讲过的都要算数）。 |
| 根因（已核实） | ① `llm_server` 是**完全无状态**的：`routers/chat.py:36-38` 的 `_new_conversation_id()` 注释原文即「服务端无状态，仅回显透传」，`_build_messages()`（:71-84）**只渲染当前这一次的 query + inputs，不含任何历史**；② `teacher_page.dart:154-157` 每次追问只发「KP 名 / 类型 / 定义 / 原文 + 当前这一个问题」，**从不带历史**；③ Dify 那套真正的服务端多轮会话代码在仓库里是**整段注释掉的死代码**（`dify_client.dart:333/339/343/439-475`），`AiProvider.protocol` 的 `dify` 也标着「已停用」。 |
| 结论 | **多轮上下文 100% 靠客户端注入**。现成先例：AI 助手 Tab 的 `_buildSessionContext()`（`agent_page.dart:722-735`）把本会话最近的问答拼进 query 再发出去。**本次老师模式必须照此实现**（§7.1 的 L2 层）——只把两个 Tab 合成一个是**不够**的，合并 UI 与注入上下文缺一不可。 |
| 性质判定 | **缺陷修复 + 能力补齐**（本次改造的真正用户价值所在）。验收见 §9-B3 / §9-B5。 |
| **价值定位（已确认）** | 本次需求的真正价值 = **补上多轮记忆**；「合并两个 Tab」只是**表象**。用户要的「继续用这个会话」**必须**靠 L2 上下文注入才能成立。因此设计阶段应把「L2 注入生效」当作**首要目标**对待，合并 Tab、合并会话列表等是达成它的载体。**最高优先级硬验收 = §9.2 的 T6**（连续追问 3 轮，第 3 轮须能引用第 1 轮内容）——此项不通过，本次改造的核心价值即未成立。 |

## 2. 合并后的产品形态（本次核心）

### 2.1 形态定义

老师模式从「双 Tab 双会话」改为「**单会话流**」：

> 进入知识点 → 自动打开该知识点的**主会话** → 若主会话尚无任何 assistant 消息，则**自动生成一次讲解**（T6）并作为该会话的**第一条 assistant 消息**落库 → 之后用户在同一会话里继续追问（T5），**讲解与追问是同一条消息流里的内容，不再分 Tab**。

| 维度 | 现状 | 目标 |
| --- | --- | --- |
| 页面结构 | TabBar「讲解 (T6)」「追问 (T5)」+ TabBarView | **单消息流**（用户右气泡 / AI 左气泡），无 Tab |
| 会话数（每 KP） | 固定 2 条（chat + explain） | **N 条**（1 条主会话 + 用户自建若干）；T5 与 T6 **共用同一条会话行**（见 §10.1-D4） |
| 讲解的载体 | 内存变量 `_explainText`（退出即失） | **会话内的 assistant 消息**（落库、永久可见） |
| 追问的载体 | chat 会话消息 | 同一个会话的消息流 |
| 上下文 | 讲解不带追问上下文；追问**完全不带历史**（§1.4：多轮无记忆） | 同一会话内，**知识点上下文 + 会话历史**共同注入（见 §7.1 L2） |
| 会话管理 | 无 | 列表 / 新建 / 切换 / 重命名 / 清空 / 删除（见 §4） |
| 会话行的类型 | `type` 分为 `'chat'`（T5）与 `'explain'`（T6）两种 | 老师模式统一为 **`'chat'` 单一值**；历史 `'explain'` 行由 §5 合并消化（迁移失败时残留行仍可见，见 §4.1） |

### 2.2 完整用户旅程

**旅程 1：首次进入知识点（无任何历史）**

1. 用户在知识树点节点（或从知识点管理页点「追问」）→ 打开老师模式页。
2. 页面加载 `_KpHeader`（知识点名 / 类型 / 置信度 / 定义 / 原文）+ 消息流区（此时为空，显示「正在生成讲解…」占位）+ 底部输入框。
3. 系统定位主会话：不存在则创建（type=`chat`、kpId=该知识点；标题规则见 §4.1）。
4. 主会话为空 → **自动生成一次讲解**（T6，流式），流式气泡实时增长。
5. 讲解落库为该会话的**第一条 assistant 消息**（带「讲解」小标签，判别见 §4.5）。
6. 之后用户可在同一输入框继续提问（T5），回答以气泡追加。

**旅程 2：二次进入知识点（已有讲解）**

1. 进入 → 定位主会话 → 读出该会话消息流 → **直接渲染历史讲解与历史追问**（不再显示「暂无讲解」）。
2. **不重复自动讲解**：仅当主会话**没有任何 assistant 消息**时才自动生成。
3. 用户可继续提问；新消息追加在流末尾。

**旅程 3：用户主动「新建会话」（不自动讲解）**

1. 用户点 AppBar「新建会话」图标（或会话面板顶部的「新建对话」）—— 按钮语义提示写明「**新会话从提问开始，不会自动讲解**」。
2. 系统在**同一知识点下**新建一条会话（type=`chat`、kpId=该知识点、title 留空 → 运行时派生）。
3. 新会话为空 → **不自动讲解**（用户意图是「换个话题提问」，不是要一份新讲解）；新会话直接进入「提问」状态，消息流为空。
4. 用户提问 → 消息写入新会话；该会话成为「当前会话」，其 `updatedAt` 刷新 → 列表置顶。

> **两条路径刻意不同（已拍板）**：用户**主动**新建 → 不自动讲解；**删除主会话后系统补建** → 自动讲解（见旅程 5 / §3.3）。依据与理由见 §10.2 Q1。

**旅程 4：切换会话**

1. 用户点 AppBar「会话列表」图标 → 打开会话管理面板（复用 `_SessionManagerSheet` 交互模式）。
2. 列表按**最近活跃在前**展示：标题（重命名优先，否则运行时派生）、消息数、最近活跃时间、最后一条消息预览。
3. 点某条会话 → 关闭面板，消息流整体替换为该会话的消息；输入框清空。
4. 切换后若目标会话为空消息 → 显示空态引导「这个会话还没有内容，问点什么吧」。

**旅程 5：删除会话（含主会话）**

1. 会话面板 → 该会话的「⋮」菜单 → 「删除该会话？」→ **二次确认**。
   - 删除**非主会话**：确认文案「连同消息一起删除，不可恢复」。
   - 删除**主会话**：确认文案为**全 PRD 唯一版本**（Q1/Q4 合并定稿，见 §4.4）：
     > 「这是该知识点的默认会话。删除后将自动切换到『{下一个会话标题}』；若无其它会话，将新建一条并自动生成一次讲解。确定删除？」
2. 确认 → 软删会话行 + 其全部消息（`deleteSession` 既有实现）→ 列表刷新。
3. **删除主会话的特殊处理（已拍板）**：主会话被删后自动**顺延**到该知识点下剩余的下一条会话并自动打开 + 提示「已切换到会话『X』」；若该 KP 下已无任何会话，则**新建一条并自动讲解**（见 §3.3）。
4. 被删会话的消息**不在任何界面复现**（软删铁律：所有列表查询过滤 `deleted_at`）。

## 3. 主会话的定义（已拍板）

### 3.1 结论

> **主会话 = 该知识点（kpId）下「最早创建且未删除」的那条会话。**
>
> 判定式：**该 KP 下未删除会话中 `id` 最小者**——`ai_sessions` 主键是 **ULID，单调递增**，故 `id` 最小 ≡ 最早创建；无需新增任何列。

判定式（供工程师实现）：

```
主会话 = min( { s ∈ ai_sessions | s.kp_id = K AND s.type = 'chat' AND s.deleted_at IS NULL } by id )
-- 实际 SQL 形态：
-- SELECT * FROM ai_sessions
--  WHERE kp_id = ? AND type = 'chat' AND deleted_at IS NULL
--  ORDER BY id ASC LIMIT 1
```

说明：
- `ai_sessions` 表**没有 created_at 列**（`SyncMeta` 仅 `version / updated_at / device_id / deleted_at`），ULID 的单调性是本判定的依据；本仓库已有同源先例：`agent_page.dart` 的会话列表用 `OrderingTerm.desc(t.id)` 作为同毫秒的次级排序。
- 判定**只看未删除会话**；§5 迁移完成后，原 `explain` 会话行已被软删，自动退出候选集，不会干扰主会话判定。
- 类型归一：老师模式会话统一为 `type='chat'`（老数据里 `explain` 类型由 §5 迁移消化；单独存在的 `explain` 行按 §5.2 补充规则归一）。**`type='chat'` 这一条件的作用**：当合并失败、残留 `type='explain'` 行时，它**不会**抢走主会话（避免用户只看到讲解、追问仍在另一条会话里）。
- **加载顺序约束（实现必须遵守）**：**先执行「explain→chat 合并（含 type 归一）」→ 再取主会话**。否则遗留的 `explain` 行可能因 id 更小而抢成主会话（`teacher_page` 的 `_bootstrap()` 里两步的先后顺序即为此约束的落点）。

### 3.2 表结构结论（已拍板）：**不新增 `isPrimary` 列，不改表结构**

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| **A. 不改表（用户已拍板）** | 纯靠「kpId + 墓碑过滤 + ULID 序」推导 | ① 用户无法手动指定主会话；② 删除主会话后主会话会顺延（由 §3.3 规则收敛体验） | **采纳（最终结论）** |
| B. 改表加 `is_primary` | 可显式标记、可手动指定 | 需改表 + `schemaVersion` 迁移 + 手工复刻 `.g.dart`（沙箱禁跑 build_runner）；同步 payload 要加字段 → 服务端 schema 外溢；flag 与「最早会话」两套语义并存易不一致 | **不采纳**（列为 P2 备选，若将来用户明确要求「可指定主会话」再评估） |

### 3.3 主会话相关的边界规则

| 情形 | 规则 |
| --- | --- |
| 进入知识点时该 KP 下**无任何未删除会话** | 新建一条主会话（type=`chat`、kpId=该知识点）并**自动讲解一次**（§2.2 旅程 1） |
| **删除主会话** | 主会话**自动顺延**到该 KP 下的下一条会话（未被删除的最小 id），并自动打开它 + 提示「已切换到会话『X』」 |
| 删除主会话后该 KP 下**已无任何会话** | **新建一条并自动讲解**（保证「进入知识点即有讲解」的不变量，与首次进入一致） |
| 用户新建的会话 | 通常不是主会话（最新创建 ≠ 最早）；仅当更早的会话都被删除后才可能成为主会话 |
| 主会话被重命名 | 不影响主会话身份（标题与身份解耦） |
| 多端并发 | 主会话在**各自本地库**内判定；`ai_sessions` 参与同步，理论上跨端趋同；ULID 序依赖设备时钟，跨设备时钟偏差可能导致两端判定不同 → **已知限制**，登记 P2 观察项 |

| 动作 | 语义 | 实现 | 二次确认 | 用户可见差异 |
| --- | --- | --- | --- | --- |
| **清空消息** | 保留会话行，删除其全部消息 | `clearMessages`（消息软删，行保留） | ✅ 文案：「会话会保留，消息不可恢复」 | 会话仍在列表（消息数 0），主会话身份不变 |

| **删除主会话** | 同上，但触发 §3.3 的顺延 / 补建规则 | 同上 | ✅ **全 PRD 唯一版本文案（Q1+Q4 合并定稿）**：「这是该知识点的默认会话。删除后将自动切换到『{下一个会话标题}』；若无其它会话，将新建一条并自动生成一次讲解。确定删除？」 | 删除后自动顺延并打开下一条会话 + 提示「已切换到会话『X』」；无其它会话则新建并**自动讲解** |

- **文案一致性铁律**：主会话删除确认的这段文案，在「删除主会话」「§3.3 补建提示」「会话列表菜单」三处**必须逐字一致**（同一份常量），不得各写一套。

- 两者均为**软删**，不物理删行（留墓碑供同步传播）；列表查询必须过滤墓碑，删除后任何界面不得复现。
- 均登记 outbox（`upsertAiSession` / `upsertAiMessage`），保证跨端删除可传播。
- 不提供恢复入口（与 Agent 现状一致，回收站为 P2 候选）。
- ⚠️ **跨端删除语义（已核实）**：同步层对 `deleted_at` 非空的远端行是**硬删本地行**（`sync_engine.dart:20` 注释「`remote.deletedAt != null` → 硬删除本地对应行」）→ **对端会话是「彻底消失」，不是「变灰/墓碑」**。因此：① PRD 不得承诺「删除的会话在其它设备上仍可见或可恢复」；② 若将来做回收站，**只能是本机语义**，不能写进跨设备验收标准。

## 5. 历史数据兼容（老数据处置）

### 5.1 现状数据形态

- 老库里同一知识点下有**两条**会话：一条 `type='chat'`（T5 追问）、一条 `type='explain'`（T6 讲解），`kp_id` 都等于该知识点 id。
- 讲解消息（role=assistant，modelId=`dify-t6`）落在 `explain` 会话下；追问消息落在 `chat` 会话下。
- `_bootstrap()` 的调用顺序是 **先 T5 后 T6**，因此通常 `chat` 会话 ULID 更小（更早创建）。

### 5.2 方案（已拍板）：进入知识点时自动合并成一条

**规则**：当用户进入某知识点的老师模式时，若该 KP 下**同时存在**未删除的 `type='explain'` 会话与 `type='chat'` 会话，则：

1. **保留方 = `chat` 会话；并入方 = `explain` 会话**（方向固定：explain → chat）。
2. 把 `explain` 会话下的全部未删消息，按**时间顺序**迁入 `chat` 会话（迁入后的消息**保留每条消息的原始时间戳**，即新行的 `updated_at` 写回原值）。
3. 迁移完成后，`explain` 会话行**软删**（`deleted_at` 置位 + version+1 + 登记 outbox）——**软删行本身即「已迁移」标记**，保证迁移幂等（重复进入不再迁）。
4. 迁移后该 KP 下只剩一条会话，用户最终只看到**一条连续的历史消息流**，历史内容**一条不丢**。

**补充规则（与拍板结论不冲突的实现细则）**：
- **仅存在 `explain` 会话**（用户从未追问过）→ 不做合并，但把该行 `type` 归一为 `'chat'`（version+1 + 登记 outbox），使其可作为主会话被正常识别与展示。
- **仅存在 `chat` 会话** → 无需任何处理。
- **两条都不存在** → 走 §3.3「新建主会话 + 自动讲解」。
- **消息复制方式**：采用「**复制 + 软删原行**」——为每条 `explain` 消息新建一行（新 ULID、`session_id` 指向 `chat` 会话），原行软删。**不采用「直接改 `session_id`」**（理由见 §5.3-R1）。
- **被移动消息的字段必须原样保留（硬约束）**：`model_id` / `role` / `content_md` / **原始 `updated_at`（时间序）** 一律**原样搬运**，**只允许改 `session_id`**（以及新行的 ULID、`version` 起算）。理由：`model_id` 决定讲解/追问的视觉判别（§4.5），`updated_at` 决定消息流排序，丢任何一个都会造成「讲解标签错乱」或「时间顺序错乱」。
- **同步入队（硬约束）**：**每条**被移动的消息都要**单独入队**（`upsertAiMessage`）；`explain` 行软删要入队 `upsertAiSession`。
  ⚠️ 同步层**没有** `tombstoneAiSession` / `tombstoneAiMessage` 这两个 API——软删**靠 payload 的 `deleted_at` 传递**，不要去找不存在的接口。
- **同毫秒消息的顺序**：复制时按原顺序依次生成新 ULID（单调递增），保证同毫秒消息的相对先后与原流一致（`updated_at ASC` + `id ASC` 排序键下可稳定还原）。
- **执行顺序（硬约束）**：**必须先完成合并（含 type 归一）→ 再取主会话**，否则遗留 `explain` 行可能因 `id` 更小而抢成主会话。详见 §3.1、§8.2 实现约束 IC2。

### 5.3 风险评估与缓解（方案已定，此处为实现要求）

| # | 风险 | 影响 | 缓解 / 实现要求 |
| --- | --- | --- | --- |
| R1 | **消息复制 vs 改 session_id**：若直接把原消息行的 `session_id` 改为 `chat` 会话 | 同一消息 id 的 payload 发生变化 → 在途同步可能回声覆盖；违背 append-only 语义 | **强制采用「复制 + 软删原行」**：新建消息行（新 ULID、指向 chat 会话），原行软删。`model_id` / `role` / `content_md` / 原始 `updated_at` **原样保留**。append-only 保持，旧端收到墓碑、新端收到新行，最终一致 |
| R2 | **迁移失败导致讲解丢失** | 用户最在意的就是「讲解别丢」 | 迁移全程 try/catch：**失败不阻断进入页面**、不删除任何数据；`explain` 会话作为独立会话**继续留在列表中**（用户可点进去看原讲解），并 toast「历史讲解迁移失败，已保留为独立会话」 |
| R3 | **重复迁移** | 产生重复消息 | 幂等键 = 「`explain` 会话行已被软删」；复制前再检查目标会话是否已存在同 `content_md + 角色 + 时间戳` 的消息（防御性） |
| R4 | **同毫秒消息顺序歧义** | 讲解与追问先后可能颠倒一次 | 复制时按原顺序依次生成新 ULID，保证 `updated_at ASC` + `id ASC` 下顺序可稳定还原；顺序错乱最多影响一次阅读体验，**不丢消息** |
| R5 | **迁移时机** | ① 进入时懒迁移：只处理用户真正打开的 KP，零后台扫描成本；② 升级后一次性批处理：库干净，但全局扫描 + 写放大 + 与同步交互复杂 | **采纳懒迁移（进入知识点时触发）**；批处理列 P2 可选 |
| R6 | **同步交叉**：迁移产生的「新消息 + 旧消息墓碑」上行 | 其它设备短暂看到重复内容 | 墓碑 + 新行同批上行，接收端按墓碑过滤；若同步层出现重复，登记 P2 观察项 |
| R7 | **`type` 归一（`explain` → `chat`）的同步可见性** | 另一端可能短暂看到 `explain` 类型的会话 | `type` 在同步 payload 内，归一后随 outbox 上行，最终一致；本地判定以未删除会话 id 最小为准，不依赖 type |

**被否决的替代方案**：不做迁移、让 `explain` 会话作为「只读历史讲解」继续留在列表——零风险，但用户仍看到两条会话、且要手动点进去才能看到原讲解，与「合并成一条」的拍板结论不符，**不采纳**。

### 5.4 用户可见影响

| 场景 | 用户看到的变化 |
| --- | --- |
| 首次进入某知识点 | 该 KP 下原本两条会话 → **合并为一条**；原讲解作为该会话中按时间顺序排列的一条消息出现（**内容不变、时间不变、一条不丢**） |
| 会话列表 | 该 KP 下条目数从 2 变 1；主会话带「默认」标签 |
| 同步到其它设备 | 旧设备可能短暂看到两条会话（墓碑未到达前），最终一致 |

### 5.5 迁移可观测性

| 项 | 规定 |
| --- | --- |
| 日志 | 用 `AppLog` 记录：迁移发生（kpId、chat 会话 id、explain 会话 id、迁移消息条数）、跳过（原因：已是单会话 / 已迁移过 / 仅 explain 并做 type 归一）、失败（异常 + 两侧 id） |
| 失败提示 | 非阻塞 toast / banner，绝不静默失败、绝不阻断进入 |
| 计数 | 迁移成功/失败次数需在应用日志中可检索（便于首轮灰度排查） |
| 测试 | 需覆盖：只有 chat / 只有 explain（走 type 归一）/ 两条都有（explain→chat 合并）/ explain 已软删（幂等）/ 迁移抛异常（回退保留 explain 会话）/ 同毫秒多消息顺序 六种场景 |

## 6. 「重新生成讲解」的处置（已拍板）

| 项 | 规定 |
| --- | --- |
| 结论 | **「再讲一次」= 追加一条新的 assistant 消息，不覆盖历史**；历史讲解全部保留、可对比（append-only 语义） |
| UI 文案 | 按钮文案由「重新生成」改为「**再讲一次**」；不再有任何覆盖式行为 |
| UI 位置 | **消息流底部、与输入框同区**（输入框上方一行，靠右对齐；常驻可见，生成中显示 loading 并禁用）；**不单独占一个 Tab**、不放 AppBar 顶级入口 |
| 消息呈现 | 生成结果作为**新的一条 assistant 气泡**追加到流末尾（流式增长），带「讲解」小标签，与历史讲解并列可对比 |
| 落库 | 写入**当前会话**（主会话或用户当前打开的会话），不是新会话；写入的 `model_id` 用**讲解值**（`dify-t6`），与追问消息（`dify-t5`）区分、与 §4.5 判别规则一致 |
| 上下文 | 携带知识点上下文 + 该会话最近若干轮历史（§7），保证「再讲一次」与前文连贯、不会每次都从零讲起 |
| 旧行为 | 原「重新生成」覆盖式逻辑下线（不存在覆盖历史的情况） |

## 7. 会话上下文与多轮

### 7.1 「会话上下文」的定义

本次明确为三层，自上而下：

| 层 | 内容 | 注入方式 |
| --- | --- | --- |
| L1 知识点上下文 | 知识点名称、类型、定义、来源原文（`kp.sourceQuote`） | 每次请求都注入（现状已有，见 `teacher_page.dart:154-157`） |
| L2 会话历史 | **当前会话内**此前的 user / assistant 消息（按时间序） | 注入最近 N 条（M 取值见 §7.4）；**实现参照 `agent_page._buildSessionContext()`** |
| L3 服务端会话态 | Provider 侧的 `conversationId`（仅标签，无记忆，见 §7.2） | 透传（见 §7.3） |

**L2 是本次新增的关键，且是本次真正的用户价值**：现状下追问只带 L1，**完全不带历史**（§1.4：多轮追问当前无记忆）；合并后同一会话内 AI 能看到用户刚问过什么、自己刚讲过什么。**只把两个 Tab 合成一个是不够的——UI 合并 + L2 注入缺一不可。**

### 7.2 现状事实（已核实，直接影响设计）

- **llm_server 完全无状态**：`routers/chat.py:36-38` 的 `_new_conversation_id()` 注释原文即「**服务端无状态**，仅回显透传」；`:132` 收到 `conversation_id` 原样回传、收不到就现生成一个；`_build_messages()`（:71-84）**只渲染当前这一次的 query + inputs，不含任何历史**。
- 因此**多轮连贯必须由 App 侧注入历史（L2）**来保证，**不能依赖服务端会话态**。
- 客户端现成先例：AI 助手 Tab 的 `_buildSessionContext()`（`agent_page.dart:722-735`）把本会话最近的问答拼进 query 再发出去——**老师模式照此实现即可，无需新机制**。
- Dify 那套真正的服务端多轮会话代码在仓库里是**整段注释掉的死代码**（`dify_client.dart:333/339/343/439-475`），`AiProvider.protocol` 的 `dify` 标着「已停用」。
- App 侧现状：追问 Tab 用 `widget.ai.chat(AiTask.t5Ask, fullQuery, conversationId: _askConversationId)`，`_askConversationId` 是**纯内存态**（`teacher_page.dart:168-170`），App 重启即失效。

### 7.3 `conversationId`：术语澄清与持久化结论（已拍板 · 终稿）

**术语澄清（避免工程侧误解为「要新增 conversation_id 列」）**：本 PRD 中的 `conversationId` 只可能指以下三者，逐一裁定：

| 可能指代 | 裁定 | 理由 |
| --- | --- | --- |
| ① **Dify 的服务端会话句柄**（`AiChunk.conversationId`） | **在本项目不成立** | Dify 协议已停用（bootstrap 跳过、`dify_client` 相关代码整段注释）；且 llm_server 无状态（§7.2），该 id 只是回显标签 |
| ② **「把 T5 追问 / T6 讲解归到同一条流」的逻辑分组 id** | **由 `ai_session` 行本身承担** | 一条 `ai_sessions` 行 ≡ 一条会话流（§10.1-D4），无需独立的第二 id |
| ③ 一个 KP 下同时存在多条会话时、**独立于 session 行 id** 的「流 id」 | **不需要** | 「流」就是会话行；主会话用「id 最小者」判定即可（§3.1） |

**结论：三种情况都不需要新增列，也不需要持久化。**

| 项 | 结论（终稿） |
| --- | --- |
| 是否持久化到 `ai_sessions` 某列 | **不持久化**（已拍板） |
| 是否写进 `target_ref` | **不写**（`target_ref` 保持其既有语义） |
| 是否做跨端往返 | **不做**（不随同步传播、不指望换端后继续） |
| 理由 1 | 当前主力后端 `llm_server` **不使用** `conversation_id` 承载上下文（§7.2），持久化它**不产生任何上下文收益**，只会制造「以为有连续性」的错觉。 |
| 理由 2 | 持久化必然引入**跨端失效风险**：该 id 属某台设备 / 某个 Dify 应用，换设备、换端、应用重置后即失效；用它做上下文会得到「莫名答非所问」的体验。 |
| 理由 3 | 保持内存态与 Agent Tab 现状一致（`agent_page.dart:412` 注释即此口径），**零 schema 变更**。 |
| 多轮连贯由谁承担 | **App 侧注入 L2 会话历史**（§7.1 / §7.4），这是唯一的上下文来源。 |
| 未来演进备选 | 若将来切回 Dify 协议确需持久化 → 写入现有 `tutor_state` JSON（详见附录 B；**不改表**） |
| 降级处理（必须写进验收） | ① App 重启 / 换设备后 `conversationId` 失效 → **L2 历史注入兜底**，用户感知为「AI 仍记得刚才聊过什么」（仅限本会话历史注入范围）；② 服务端返回的 `conversationId` 与本地缓存不一致时，以服务端为准并更新本地内存态；③ L2 注入失败（超长 / 异常）→ 降级为仅 L1，并在日志中记录，不阻断回答。 |

### 7.4 L2 注入的规模约定

| 项 | 建议取值 | 理由 |
| --- | --- | --- |
| 注入范围 | **最近 12 条 user/assistant 消息（≈6 轮）**，与 AI 助手 Tab 的 `_buildSessionContext()` 现状一致 | 与既有实现同口径、少造轮子；12 条以内的话题延续足够，超过部分由更早的总结代替（本期不做总结） |
| 注入总长度上限 | 建议 ≤ 4000 字符（超限从最老的一条开始裁剪） | 控制 token 成本与延迟；具体阈值由工程师按模型上下文窗口定 |
| 裁剪策略 | 保留 L1 永远不裁；L2 从最老开始裁；**本轮用户提问永远保留** | 保证当前问题不被裁掉 |
| 触发时机 | 每次发问（`_send` 等价路径）与「再讲一次」都注入 | 保证两条路径上下文一致 |
| 注入格式 | 建议照抄 Agent 的格式：先「【本会话前文】…」段落，再逐条「用户：… / AI：…」 | 提示词侧已被 llm_server 的 query 渲染机制验证可用（Agent Tab 线上在用） |

| # | 约束 | 落点 / 理由 |

| **IC7** | **老师模式的会话列表必须用「新增的独立方法」**（如 `listTeacherSessions(kpId)`，过滤 `kp_id = K AND deleted_at IS NULL`）；**禁止修改 `listAgentSessions()` 的过滤语义**——它是 **Agent 侧专用**（`type='chat' AND kp_id IS NULL AND deleted_at IS NULL`）。两者是**两个独立方法、两条独立查询**，改一个不得影响另一个。 | §4.1；若把两者合并成一个方法再按调用方分支，Agent 侧列表会混入老师模式会话（或反之），属于把 Agent 的列表查询改坏。Agent 侧既有行为与测试必须**零变化** |

## 9. 验收清单（逐条可判定）

**A. 缺陷修复（问题 A）**
- [ ] A1 首次进入知识点 → 自动生成一次讲解并显示（流式）；讲解**落库**为该会话的 assistant 消息。
- [ ] A2 **退出页面再进入** → 屏幕上直接出现上次的讲解文本，**不出现**「暂无讲解，点『重新生成』」。
- [ ] A3 讲解在 App **完全重启**后仍可见（从 `ai_messages` 读出）。
- [ ] A4 历史追问消息同样在退出重进后可见（消息流整体回填，非只回填讲解）。
- [ ] A5 删除会话后重新进入该知识点，**不会**捞回已软删的会话行（修复 `getOrCreateForKp` 未过滤 `deleted_at`）：必须拿到**一条新会话**，而不是「已删的空壳会话」（空壳的表现是永远显示空）。
- [ ] A6 主会话**已有 assistant 消息时不重复自动讲解**（只讲一次）。
- [ ] A7 全部会话相关查询（`getOrCreateForKp` / 列表 / 消息 / 清空）**一律带 `deleted_at IS NULL` 过滤**；合并幂等性依赖此条。

**B. 合并形态**
- [ ] B1 老师模式页**不再有**「讲解 (T6)」「追问 (T5)」两个 Tab；讲解与追问在同一消息流。
- [ ] B2 自动讲解与用户追问的消息在同一列表里按时间顺序排列。
- [ ] B3 追问时 AI 能引用本会话此前的讲解内容（L2 历史注入生效，验收用例：先让 AI 讲一个含数字的例题，再问「刚才那个数是多少」）。
- [ ] B4 同一知识点下的追问与讲解**共用一条会话**（`ai_sessions` 中该 kp_id 下不新增第二条 `chat` 行）；老师模式会话 `type` 统一为 `'chat'`。
- [ ] B5 **多轮记忆（本次核心价值）**：连续追问 3 轮，**第 3 轮的回答能引用到第 1 轮的内容**（例：第 1 轮问「反向传播的例子里有数字 7.5」，第 3 轮问「刚才那个数是多少」）。**当前实现必然失败**（`teacher_page.dart:154-157` 不带历史），修复后必须通过。

**C. 会话管理**
- [ ] C1 可新建会话：新建后消息流为空、可正常提问、该会话在列表中置顶。
- [ ] C2 可切换会话：切换后消息流整体替换为目标会话的内容。
- [ ] C3 可重命名：重命名后列表标题变化，**退出重进仍保留**（落 `title` 列），且随同步 payload 传播。
- [ ] C4 可清空：清空后消息数归零、会话行仍在列表、**主会话身份不变**。
- [ ] C5 可删除：删除后该会话从列表消失，且**任何界面都不再复现其消息**（软删过滤）。
- [ ] C6 删除 / 清空均有二次确认；重命名无二次确认。
- [ ] C7 列表按最近活跃排序；每条显示标题 / 消息数 / 最近活跃时间 / 内容预览；主会话带「默认」标记。
- [ ] C8 **删除主会话**后：主会话**自动顺延**到该 KP 下的下一条会话并自动打开 + 提示；该 KP 下已无任何会话 → **新建一条并自动讲解**（生成一条讲解消息）。
- [ ] C9 老师模式会话列表**不含** Agent 会话；Agent Tab 的会话列表**不含**老师模式会话（互不混入）。
- [ ] C10 消息流长会话滚动流畅（`ListView.builder` 虚拟化生效）。

- [ ] C16 **讲解/追问判别容错**：构造 `model_id` 为空与为任意值的消息 → 按普通消息渲染，**不抛异常、不崩溃**（实现约束 IC6）。
- [ ] C17 **Agent 侧列表查询零变化**：`listAgentSessions()` 的过滤语义与返回结果**完全不变**（仍是 `type='chat' AND kp_id IS NULL AND deleted_at IS NULL`），Agent 侧既有测试全绿；老师模式走**新增的独立方法** `listTeacherSessions(kpId)`，两个列表互不混入（实现约束 IC7）。

## 附录 C：与既有铁律的兼容性声明

- **软删铁律**：会话与消息一律软删；所有列表查询过滤 `deleted_at`（本次顺带修 `getOrCreateForKp`）。
- **append-only 语义**：消息不编辑、不删除单条；「再讲一次」是追加而非覆盖；老数据迁移采用「复制 + 软删原行」而非改行。
- **不改表结构**：`ai_sessions` 表结构与 `sync_row_map` 同步字段**均不变**（无新增列、无新增 payload 字段）。
- **会话隔离**：老师模式会话（`kp_id = K`）与 Agent 会话（`kp_id IS NULL`）在所有查询中互斥。
- **写操作收口**：所有会话/消息写操作走 `AiSessionRepository`（禁止 UI 直写表），并统一登记 outbox。
